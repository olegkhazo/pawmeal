# CLAUDE PROJECT RULES — PET FOOD SUBSCRIPTION MVP / GEORGIA

Этот файл является спецификацией и дорожной картой. Прочитай целиком перед работой. Создай рабочий проект по этапам, проверяя каждый этап. Не ограничивайся макетом или описанием. Общайся с владельцем на русском. Код, типы, имена файлов и ключи переводов — на английском.

## 1. Цель и границы

Проверить спрос в стране Грузия на регулярную доставку приготовленного питания для собак и кошек в порционных пакетах. Пользователь видит лендинг, выбирает питомца, проходит quiz, получает предварительное предложение, оставляет телефон и продолжает общение с оператором через WhatsApp или Telegram.

Основная конверсия — успешно сохранённая заявка с валидным телефоном и согласием на связь. Это заявка на интерес к будущей подписке, а не действующая подписка. Дополнительная конверсия — нажатие кнопки мессенджера; оно не доказывает, что сообщение отправлено.

В MVP нет оплаты, автосписаний, корзины, клиентского кабинета, доставки, склада, ветеринарной диагностики, AI-анализа здоровья, сложной CRM. Один питомец на анкету; для второго можно заполнить новую. Не добавляй функции вне этой спецификации.

Временный бренд: PawMeal Georgia, полностью настраиваемый. Не заявляй регистрацию бренда или доступность домена. На сайте коротко и заметно объясни: «Готовим запуск доставки в Грузии. Оставьте заявку — обсудим питание, стоимость и доступность в вашем городе. Оплата сейчас не требуется».

## 2. Референсы и контент

https://www.foodforjoe.es/
https://www.differentdog.com/
https://www.smalls.com/

Используй их как источники структуры и продуктовых механик: выбор вида питомца, акцент на приготовленном питании, визуальный каталог рецептов, персонализация через анкету, объяснение подписки, повторные CTA, FAQ. Food for Joe — основной ориентир для разделения собак/кошек; Different Dog — для подачи разнообразия рецептов; Smalls — для выразительного раздела кошек.

Перед реализацией изучи доступные страницы и запиши ссылки и выводы в docs/references.md. Если страница недоступна, честно отметь это и продолжай по спецификации. Не копируй тексты целиком, дизайн пиксель в пиксель, фотографии, логотипы, отзывы, рейтинги, исследования и статистику брендов. Перепиши идеи оригинально под наш пилот в Грузии.

Запрещено выдумывать реальные отзывы, число клиентов, работающие производственные мощности, сертификаты, ветеринарное одобрение, состав и пищевую ценность, лечебные эффекты, обещания долголетия, бесплатную доставку, гарантии и уже действующие зоны доставки. Не называй концепты полнорационными или подходящими при болезнях без подтверждения производителя и специалиста. На карточках: «Концепт рецепта. Состав и доступность уточняются перед запуском».

## 3. Технологии

Для нового репозитория: Nuxt с Vue 3, TypeScript strict, Tailwind CSS, Pinia только для состояния quiz при необходимости, Nuxt i18n, Zod, libphonenumber-js, Nitro server routes, PostgreSQL + Prisma. Используй актуальные совместимые стабильные версии после проверки официальной документации; зафиксируй lockfile. Если проект уже существует, сначала изучи его и сохрани совместимый стек, не переписывай всё автоматически.

SSR/пререндер лендинга, серверное сохранение лидов. Node LTS, обычное развёртывание с HTTPS; не привязывай архитектуру к одному хостингу. PostgreSQL локально через docker compose; DATABASE_URL для внешней БД. Не рассчитывай на SQLite или файлы на эфемерном сервере для production.

Vitest для логики и Playwright для основных сценариев. npm scripts: dev, build, preview, typecheck, lint, test, test:e2e. README с точными командами запуска, миграций и production deployment.

## 4. Страницы и визуальный стиль

Маршруты: /ka, /ru, /en; /{locale}/quiz; /{locale}/thank-you; /{locale}/privacy. Корень перенаправляет на ka. Валидируй locale и предоставь локализованный 404. Результат анкеты — последний шаг quiz, до формы контакта. Thank-you без телефона или ответов в URL.

Mobile first. Светлый тёплый фон, графитовый текст, один зелёный акцент, мягкие карточки, большие фотографии пакетиков и еды, чистая типографика. Фотографии должны визуально различать рецепты. Удобный интерфейс на 360px и до широкого desktop. Грузинский шрифт с настоящей поддержкой алфавита, например Noto Sans Georgian, плюс подходящий Latin/Cyrillic; проверь загрузку и fallback. Не используй флаги как единственный идентификатор языка: ქართული / Русский / English.

Лендинг:
1. Header: временный бренд, «Как работает», «Меню», «Вопросы», язык, CTA.
2. Hero: «Питание для вашего питомца — с регулярной доставкой»; подпись про подготовку запуска в Грузии; выбор «Для собаки» / «Для кошки», каждый запускает quiz с предвыбранным видом.
3. Короткая ценность: удобные порционные пакеты, выбор меню, обсуждение графика доставки. Только проверяемые характеристики будущей концепции.
4. Как это работает: анкета → предварительный выбор → обсуждение с оператором → согласование пилотной доставки.
5. Каталог из 6 концептов рецептов с фильтром собаки/кошки.
6. Объяснение формата подписки: регулярность, размер пакета и стоимость будут согласованы до запуска; не обещать действующие pause/cancel функции.
7. Блок о пакетах и предполагаемом хранении. Конкретный режим и сроки хранения не выдумывать: «Уточним вместе с составом и условиями доставки».
8. FAQ: пилот, города, цена, оплата, кошки/собаки, как оставлять заявку, специальные потребности.
9. Финальный CTA, контакты при настройке, privacy, повторное обозначение пилота.

Sticky CTA на mobile не перекрывает форму, cookie banner и системную клавиатуру. CTA сохраняет выбранный вид. Product CTA передаёт recipeId как предпочтение, а не обязательное назначение. Доступность: semantic HTML, keyboard, focus states, labels, aria для прогресса, contrast, reduced-motion.

## 5. Каталог: шесть типов пакетиков

По умолчанию 6 всего, а не 6 на каждый вид:
dog-chicken: концепт курицы для собак;
dog-turkey: концепт индейки для собак;
dog-beef: концепт говядины для собак;
cat-chicken: концепт курицы для кошек;
cat-turkey: концепт индейки для кошек;
cat-fish: концепт рыбы для кошек.

Это маркетинговые концепты, не рецептуры для производства. Не переносить состав собак на кошек. Все ingredient tags означают предполагаемые основные ингредиенты; финальный состав требует отдельного подтверждения. В data/recipes.ts хранить id, species, translationKey, conceptProtein, image, imageAltKey, status: concept. Не прописывать придуманные граммовки, калории, проценты мяса или цены как факты.

Отделить recipe (тип продукта) от plan (способ и частота подписки). Допустимые предпочтения plan: полный рацион / дополнение к текущему корму / нужна консультация. Частота: еженедельно / раз в две недели / раз в месяц / пока не знаю. Для охлаждённого/замороженного формата частота должна быть проверена операционно; выбор клиента не является обещанием исполнения.

## 6. Генерация фотографий

Создай docs/image-prompts.md с готовыми заданиями для image generation и manifest из 6 карточек + hero. При наличии инструмента генерации используй его; иначе предоставь эти prompts и временные качественные placeholder-изображения, явно перечисли недостающие ассеты. Не подставляй чужие брендовые изображения и не выдавай placeholder за выполненную генерацию.

Общий prompt: «Photorealistic premium pet food concept product photography, unbranded sealed flat food pouch with subtle transparent window showing gently cooked food, warm ivory studio background, soft natural shadows, minimal muted green label area left blank for later typography, matching product family, realistic food texture, no logos, no readable text, no medical badges, no hands, no watermark. Product is a packaging concept, not an existing certified product.»

Для каждой карточки укажи species и protein: dog chicken / dog turkey / dog beef / cat chicken / cat turkey / cat fish. Отличай цветовой акцент упаковки, но сохраняй одинаковую композицию. Не добавляй ингредиенты, противоречащие карточке. Hero: композиция из нескольких пакетиков и миски, свободное место под заголовок; отдельно mobile crop. Шрифт и переводные этикетки накладывай HTML/CSS, а не генерируемым текстом.

Сохранить source assets отдельно от оптимизированных AVIF/WebP. Product 1:1, hero desktop 16:9 и mobile 4:5. Указать размеры, alt на всех языках; hero без lazy loading, остальные lazy. В публичной галерее пояснить «Визуализация будущей упаковки».

## 7. Quiz, примерно 2–3 минуты

Один экран — один смысловой шаг. Кнопки «Назад»/«Далее», прогресс, сохранение неперсонального draft в sessionStorage с version и сроком жизни. Не сохранять телефон в браузерное хранилище. Смена языка сохраняет ответы и текущий шаг. Уход назад не стирает ответы. Обновление страницы восстанавливает draft, включая шаг; после успешной заявки очистить draft.

Шаги:
1. Вид: dog/cat. Имя питомца необязательно, max 50.
2. Город: обязательно. Tbilisi, Batumi, Kutaisi, Rustavi, Gori, Zugdidi, Poti, Telavi, Akhaltsikhe, other. Отдельное поле otherCity обязательно при other, 2–80 символов. ID городов стабильны; подписи переводятся. Это страна Georgia, не штат США. Все города позволяют оставить заявку; не заявлять, что доставка уже есть.
3. Возраст: числовой возраст в годах/месяцах или однозначные интервалы; вес kg >0, species-specific sanity bounds с понятной ошибкой. Для MVP интервалы возраста: менее 1 года / 1–7 / старше 7; это сегментация, не клиническая классификация. Порода необязательна: свободный текст или «метис / не знаю».
4. Активность: low/medium/high; currentFood: dry/wet/homeCooked/mixed/other.
5. Известные реакции на ингредиенты: none / chicken / turkey / beef / fish / other / unknown. none и unknown исключают остальные. other — текст max 300. Отдельный вопрос: «Есть ли назначенная ветеринаром специальная диета?» yes/no/unknown. Не требовать медицинские документы.
6. Предпочтения: выбранные рецепты только своего вида; полный рацион/дополнение/помогите выбрать; желательная частота.
7. Текущие ежемесячные расходы на корм в GEL: числовое необязательное поле ≥0 и «не знаю». Готовность рассмотреть подписку: yes/maybe/no; все варианты допускают завершение.
8. Предварительное предложение: выбранные концепты, город, план/частота, оговорка о проверке состава. Отдельно показать тестовую цену только если владелец настроил её; затем спросить «Рассмотрели бы такой вариант по этой цене?» yes/maybe/no. Не показывать придуманную цену по умолчанию.
9. Контакт: телефон обязательно, имя владельца необязательно, предпочитаемый канал WhatsApp/Telegram/звонок. Для Telegram необязательный @username с валидацией. Обязательный непредвыбранный checkbox согласия на обработку заявки и связь; отдельное необязательное согласие на маркетинг. CTA: «Оставить заявку на подписку».

Пример рекомендаций: детерминированный фильтр species → исключить выбранные проблемные conceptProtein → поднять выбранные предпочтения. При specialDiet=yes или неизвестном/other аллергене не утверждай пригодность; результат «Нужно уточнить питание со специалистом» и сохранить лид. При нулевом числе доступных концептов показывай консультацию, не возвращай исключённый продукт. Не рассчитывать лечебные диеты, суточные нормы и точную стоимость без валидированных продуктовых данных. Разница weight/age/activity помогает сегментации, не создаёт ложную клиническую персонализацию.

## 8. Сбор лидов и данные

POST /api/leads; серверная Zod-валидация независимо от frontend. Использовать libphonenumber-js для E.164, defaultCountry GE, разрешать международные номера. Маска +995 удобна, но не запрещает иностранные номера. Не считать синтаксическую валидность подтверждением владения номером — OTP вне MVP.

Lead: id UUID, createdAt UTC, locale, species, cityId, otherCity, petName?, ageBand, weightKg, breed?, activity, currentFood, excludedProteins[], otherReaction?, specialDiet, preferredRecipeIds[], planType, frequencyPreference, monthlyBudgetGel?, subscriptionInterest, priceExperimentId?, offeredMonthlyPriceGel?, priceInterest?, recommendedRecipeIds[], needsConsultation, ownerName?, phoneE164, preferredChannel, telegramUsername?, contactConsentAt, marketingConsentAt?, consentVersion, privacyVersion, utmSource/Medium/Campaign/Content/Term, landingPath, referrerOrigin?, experimentVariant?, clientRequestId unique.

Цена эксперимента определяется серверной конфигурацией, клиент не может подменить её. Не сохранять весь произвольный URL/referrer query: там могут быть персональные данные. Ограничить длины UTM. Никаких секретов в client payload.

Таблицы Lead и LeadActivity для статусов new/contacted/qualified/notInterested и ручных заметок/выбранного пакета после общения. Activity содержит минимум нужных полей, не полную копию анкеты. Чувствительные контактные данные недоступны публичным API.

Idempotency: clientRequestId один на submission attempt, сохраняется при network retry, unique constraint исключает дубль повторного клика. Существующий idempotency key возвращает прежний успешный ответ без публичного поиска по телефону. Disabled button при отправке. Ответ {leadId, success:true}; никаких phone/answers в URL и аналитике. При ошибке показывать локализованное сообщение и retry, не redirect в мессенджер. БД — источник истины; уведомление оператору не является сохранением заявки.

Anti-spam: hidden honeypot, серверный rate limit с совместимым production storage (не только память процесса), лимит body, проверка origin при нужной конфигурации. Не использовать только минимальное время заполнения, оно может блокировать восстановленные draft. Логи не содержат телефоны, username, свободные ответы или полный request body.

Экспорт: защищённый server-side CLI export-leads в CSV, доступный оператору через серверный доступ, не публичная страница. Защита от CSV formula injection для значений, начинающихся с =,+,-,@. README описывает фильтры по периоду/городу/языку и удаление лида по id. Публичного /admin без надёжной авторизации быть не должно. Dashboard вне MVP.

## 9. WhatsApp и Telegram

Только после успешного сохранения показать thank-you, lead reference и две настроенные кнопки. Перейти в мессенджер должен сам пользователь; не отправлять сообщения от его имени и не утверждать, что оператор уже написал.

WhatsApp: https://wa.me/{businessNumberDigitsOnly}?text={encodeURIComponent(localizedMessage)}. Сообщение: «Здравствуйте! Я оставил(а) заявку на питание. Номер заявки: …». Телефон бизнеса — конфигурация. Не передавать чувствительные ответы в ссылке.

Telegram manual: https://t.me/{businessUsername}, без обещания автоматического заполнения текста; рядом «Скопировать сообщение» с lead reference. Номер телефона клиента не даёт гарантированной возможности написать ему в Telegram. Альтернатива — отдельно реализованный bot с /start opaqueToken, ограниченным сроком действия и привязкой server-side; без bot использовать только username link. Не подставлять телефон/JSON анкеты в Telegram start.

Если контакты не настроены — кнопки скрыты, остаётся подтверждение сохранения заявки. Если выбран канал звонок — показать «Свяжемся по указанному номеру», без обещания конкретного срока. Сохранённая заявка остаётся валидной даже без клика мессенджера.

## 10. Три языка

ka — default, ru и en полностью равноправные. Все строки в locales/ka.json, ru.json, en.json: навигация, карточки, CTA, валидация, FAQ, consent, ошибки API, metadata, thank-you, messenger text, alt. Никакого смешанного языка или хардкода в компонентах.

lang attribute, hreflang ka/ru/en и x-default, canonical для каждой версии, sitemap. Язык задаёт URL; переключатель сохраняет контекст quiz. Не делать принудительное geo/IP-перенаправление. Грузинский перевод подготовить полностью; пометить в внутреннем launch checklist необходимость вычитки носителем. Не маркировать машинный перевод как проверенный человеком.

## 11. Цены и эксперимент

Без утверждённой экономики по умолчанию PRICE_TEST_ENABLED=false: «Стоимость обсудим после анкеты». Конфигурация должна позволять включить проверку цены в GEL и задать отдельные сценарии species/weightBand/planType, version и experimentId. Только владелец утверждает числа. При отсутствующей цене сегмента не подставлять произвольную.

При включённом эксперименте показать до сбора телефона «Предварительная цена для теста: X GEL/месяц; финальные условия подтвердим до запуска», записать показанное предложение и ответ на него. Не смешивать ready-to-buy по цене и общие лиды без цены в отчёте. Не добавлять фальшивую скидку, таймер или дефицит.

## 12. Аналитика для проверки гипотезы

События: landing_view, species_selected, quiz_started, quiz_step_completed(stepId), quiz_completed, recommendation_viewed, price_offer_viewed, price_interest_selected, lead_submit_success, lead_submit_error(errorCode), messenger_clicked(channel). Создать типизированный единый tracking adapter; analytics отключены до настройки/необходимого согласия. Не загружать Meta Pixel/GA автоматически до выбора consent при выбранной такой политике. Privacy текст должен соответствовать фактическим инструментам, не выдумывать юридическое соответствие.

Не отправлять телефон, имя, Telegram username, petName, вес конкретного питомца, диагнозы, свободные тексты или полные ответы в стороннюю аналитику. Для группировки использовать locale, species, cityId из фиксированного списка, planType, experimentVariant. Lead ID не передавать третьей стороне без необходимости; messenger_clicked — действие на кнопке, не подтверждённый диалог. Server-side lead count — источник истины для заявок. Analytics blockers могут создавать расхождения.

docs/measurement.md: visitors → quiz starts → quiz completions → saved leads → messenger clicks → manually contacted → qualified → accepted price. Формулы: quiz start rate = starts/visitors; completion = completions/starts; lead conversion = unique saved leads/visitors; CPL = ad spend/unique saved leads; qualified CPL = ad spend/qualified leads. Отдельные срезы по городу, языку, виду, кампании и цене. Опиши ограничения: заявка не равна оплате, небольшой sample не доказывает рынок, клики не равны чатам. Не задавать выдуманные «нормальные» пороги без тестового бюджета и экономики владельца.

## 13. Конфиденциальность и launch configuration

Privacy: какие поля собираются, цель связи по запросу, кто оператор, контакт для удаления, фактические получатели/провайдеры, срок хранения, отдельный маркетинг. Не придумывай юрлицо, адрес, правовое основание или универсальную гарантию соответствия законам. Срок хранения — настройка владельца с явным документированным значением; добавить CLI очистки по сроку. Данные защищены HTTPS и server-side credentials.

В .env.example: DATABASE_URL, PUBLIC_SITE_URL, BRAND_NAME, BUSINESS_WHATSAPP_NUMBER, BUSINESS_TELEGRAM_USERNAME, OPERATOR_CONTACT_EMAIL, DATA_RETENTION_DAYS, PRICE_TEST_ENABLED, ANALYTICS_PROVIDER и необходимые ключи без настоящих секретов. Приватные значения не попадать в runtimeConfig.public. Не коммитить .env, БД, выгрузки лидов. Production startup валидирует обязательные переменные. Launch checklist требует заполненных реальных контактов оператора/privacy и работоспособной БД; локальные placeholder допускаются, production не считается готовым с ними.

## 15. Поэтапная дорожная карта

Этап 0 — изучение. Проверить репозиторий и инструкции, доступные инструменты, референсы, актуальную официальную документацию. Создать docs/progress.md с этапами, решениями и unresolved items. Записать, что бренд, цены, финальные рецептуры, контакты и производство пока конфигурационные. Продолжать с безопасными defaults, не останавливать всю разработку ради этих данных.

Этап 1 — foundation. Nuxt/TS/Tailwind/i18n, маршруты, шрифты, общие компоненты, .env.example, PostgreSQL/Prisma. Проверка: установка по lockfile, запуск, ka/ru/en, typecheck/build.

Этап 2 — лендинг. Собрать все разделы и 6 карточек, обе ветки животных, оригинальные тексты и metadata на трёх языках, prompts/manifest и доступные ассеты. Проверка 360px/390px/768px/1440px, переключение языка, CTA и species preselection, отсутствие неподтверждённых claims.

Этап 3 — quiz. Полный путь, город и otherCity, conditional fields, back, progress, resume draft, language switch, алгоритм предварительных рекомендаций. Проверка собаки/кошки, исключения protein, special diet, ноль подходящих рецептов, обязательный город, weight errors, клавиатура mobile.

Этап 4 — реальные заявки. БД и миграции, POST API, client/server validation, consent timestamps/version, idempotency, rate limit, защищённые CLI. Проверка реального сохранения, double-click/network retry, БД unavailable, invalid payload, CSV injection. Нельзя назвать этап готовым, если заявки существуют только в localStorage или console.log.

Этап 5 — коммуникация и аналитика. Thank-you, wa.me, t.me + copy, все события, UTM, конфиг тестовой цены. Проверка отсутствующих контактов, URL encoding, запрета redirect до сохранения, отсутствия PII в network analytics.

Этап 6 — качество. Unit и E2E, все переводы, accessibility, изображения и layout, public SEO, privacy. Прогнать production build, lint/typecheck/tests. Performance ориентир: LCP ≤2.5s, CLS ≤0.1, INP ≤200ms; это цели, не гарантии по локальному тесту. Отчёт сохраняет реальные условия измерения.

Этап 7 — передача и запуск. README, инструкции установки/migrations/deployment, backup/restore и retention, список конфигураций владельца, launch checklist, measurement guide. Готовить deployable проект; не запускать рекламу, не публиковать и не писать людям без инструкции владельца. Отдельно честно назвать недостающие изображения, непроверенный грузинский перевод или незаполненные production поля. При устранении блокеров проводить smoke test на реальном HTTPS домене.

После каждого этапа обновлять docs/progress.md: done / next / validation / blockers. Небольшие понятные git commits, если репозиторий используется. Не менять независящие части существующего проекта. Если проверка не проходит — исправить или точно назвать блокер; не выдавать этап за завершённый.

## 16. Минимальные приёмочные сценарии

1. Georgian mobile dog path: Tbilisi → анкета → concept recommendation → +995 phone → consent → одна запись БД → WhatsApp link.
2. Russian cat path: Batumi → исключить chicken → ни одного dog recipe → international phone → Telegram + copy.
3. English otherCity path сохраняет введённый город, проходит без цены и без configured messengers.
4. Back/refresh/language switch сохраняют answers; phone не сохраняется в sessionStorage.
5. Special diet/unknown reaction → консультация, без ложного подходящего рациона.
6. Ошибка API/БД → понятная ошибка, retry, нет success/redirect; повторный запрос не создаёт дубликат.
7. Нет согласия или некорректный номер → frontend и server reject; нет публичной утечки leads.
8. Каждый lead_submit_success соответствует успешному сохранению; messenger event не считается новым лидом.
9. PRICE_TEST_ENABLED=false → никакой придуманный price; true → серверно закреплённая цена и interest в БД.
10. Production pages не содержат вымышленных отзывов, сертификатов, чужого брендинга, плейсхолдеров оператора или обещаний запущенной доставки.

## 17. Как начать работу

Сначала кратко перескажи цель, проверь репозиторий, создай progress.md и выполни этап 0. Затем последовательно реализуй этапы 1–7. Не проси владельца заново выбрать стек или архитектуру без существенного блокера. Не заменяй функциональный проект статическим скриншотом. В конце предоставь точные команды запуска, фактические результаты проверок и оставшиеся настройки до публичного теста.
